# 13. 유저 구조 설계 — 일반/회사/학교, 그룹, 그래프 철학

> 작성일: 2026-08-06 · 상태: P2-0(회원/인증) 선행 설계
> 질문에 대한 답: "그룹이 필요한가? 회사·학교는 어떻게? 페이스북처럼 연결해야 하나?"

## 0. 한 줄 결론

**일반 사용자에게 그룹은 필요 없다. 회사는 '조직 디렉토리', 학교는 '학급 그룹'이 필요하다. 그리고 잇다는 페이스북형 소셜 그래프를 만들지 않는다 — 만들 필요도, 만들어서도 안 된다.**

## 1. 그래프 철학 — 페이스북과 정반대

### 페이스북 알고리즘은 어떻게 되어 있나 (질문 답)
페이스북 피드의 고전 알고리즘 **EdgeRank**는 세 요소의 곱으로 콘텐츠를 랭킹했다: **친밀도(affinity) × 가중치(콘텐츠 유형별 weight) × 시간 감쇠(time decay)**. 현재는 수천 개 시그널의 ML 랭킹으로 진화했지만 목적은 동일하다 — **체류 시간과 참여(engagement)의 최대화**. 이 최적화는 자극적 콘텐츠를 우대하고, 관계의 양(친구 수·좋아요)을 지표로 삼는다.

### 잇다는 반대로 간다
| | 페이스북/인스타/링크드인 | 잇다 |
|---|---|---|
| 그래프 | 공개·대칭(맞팔) 네트워크, 서비스가 소유 | **비공개·비대칭 개인 수첩** — 내가 마음 쓰는 사람 목록, 나만 소유 |
| 최적화 목표 | 체류 시간·참여 | **재연결 성사 수** (North Star) — 앱을 빨리 떠나 실제 연락을 하게 만드는 것이 성공 |
| 추천 | 더 많은 연결·콘텐츠 | 하루 1명, 오래 끊긴 순 — 참여 극대화가 아니라 회복 우선순위 |
| 관계 수 | 많을수록 좋음 | 던바 수(~150) 안쪽의 깊은 관계 |
- 상대가 내 수첩에 있다는 사실은 상대에게 보이지 않는다(마음 배달을 보내기 전까지).
- 친구 추천·"알 수도 있는 사람"은 만들지 않는다 — 그래프 확장이 아니라 회복이 목적.
- 이는 기존 결정과 일관: 소셜 그래프 자동 수집 불가(#3), 익명은 회복·긍정 전용(#29).

## 2. 일반 사용자 — 그룹 없음, 연락처 기반 1:1

- **그룹 불필요.** 가족·친구·연인은 이미 '내 사람들' 수첩으로 충분하다. 그룹을 만들면 관리 비용만 생기고, 잇다의 1:1 정서(한 통의 무게)를 해친다.
- **회원 매칭**: 마음 배달의 수신자 식별은 **전화번호 해시**로 한다(카카오 로그인 시 전화번호 수집 동의 → SHA-256 해시만 저장). 내 사람 등록 시 연락처 피커에서 고른 번호의 해시가 가입자와 일치하면 "앱 사용자" 뱃지 → 앱 내 배달 가능. 미가입자는 기존 초대장 경로(#23·#30).
- 가족 그룹(부모님 안부 공유 등)은 💡 아이디어로만 — 수요 검증 전 구현 금지.

## 3. 회사 — 조직 디렉토리 모델 (질문: "팀장이 그룹을 만들라나? 자유롭게 보내게 하나?")

**답: 팀장 개설도, 완전 자유도 아닌 중간 — 회사 계약 → 조직 디렉토리 안에서 자유 발신, 그룹은 '리포트 단위'로만.**

```
Org (회사, 계약 단위)
 ├─ 관리자(HR): 도메인 이메일 검증으로 구성원 초대, 결제, 익명 집계 리포트 열람
 ├─ 구성원: 조직 디렉토리에서 동료를 찾아 감사·응원·건의 발신 (팀 무관 — 타 부서 협업이 감사의 주 대상)
 └─ Team(그룹): 팀장이 아니라 관리자가 조직도 기준 생성 — 용도는 익명 집계 리포트 단위 + 8명 룰 판정
```
- **팀장이 그룹을 만들게 하지 않는 이유**: 팀장 개설형은 "팀장이 지켜보는 방"이 되어 익명 신뢰가 죽는다(docs/05 신뢰 아키텍처). 그룹은 발신 범위가 아니라 통계 범위다.
- **자유 발신의 경계**: 조직 디렉토리 내에서만(외부인 불가) + 8명 미만 조직 익명 비활성(#40) + 아래→위·동료 간만 + 괴롭힘 유형 신고 분기(§17).
- 이메일 도메인 검증(@company.com)이 조직 소속 증명 — 별도 승인 흐름 최소화.

## 4. 학교 — 교육청 계약 → 학급 그룹 (질문 답, 단 착수는 보류 #33)

**답: 맞다 — 교육청/학교 계약 → 담임교사가 학급 그룹 개설 → 학생은 초대 코드로 참여.** 구조는 이렇게 설계하되:
- 학급 그룹 = 발신 가능 범위(같은 반 안에서만) — 전교 단위 익명은 Yik Yak의 실패 경로
- **긍정 전용**(칭찬·감사·응원), 부정 계열 완전 차단, 교사 모더레이션 대시보드 필수
- 만 14세 미만 법정대리인 동의(개인정보보호법 22조의2), 학교폭력예방법·위클래스 체계와의 관계 조사 선행
- 결정 #33 유지: 정책·승인 없이 개발 착수하지 않는다.

## 5. 스키마 초안 (P2-0)

```
member(id, provider, provider_id, nickname, phone_hash?, created_at)
org(id, name, domain, plan)          org_member(org_id, member_id, role: ADMIN|MEMBER)
team(id, org_id, name)               team_member(team_id, member_id)
class_group(id, school_org_id, teacher_member_id, invite_code)   -- 학교 트랙 승인 후
person.owner_member_id               -- 내 사람들이 회원 소유가 됨
letter.sender_member_id, letter.recipient_member_id?             -- 진짜 사용자 간 배달
```
기존 단일 사용자 데이터는 첫 로그인 시 그 계정으로 귀속(마이그레이션 1회).

## 6. 트래픽·성능 분석 (질문: "최적화할 부분은 없는지")

**현재 평가: 병목 없음.** 텍스트 전용(이미지 없음), 요청당 페이로드 수 KB, N+1 없음(연관 LAZY + 목록은 단순 쿼리), OSIV off, batch fetch 100. 개인 앱 규모(관계 수십 명)에서는 어떤 쿼리도 문제되지 않는다.

**사용자 간 기능이 열리는 순간 필요한 것 (우선순위순):**
1. **인덱스**: letter(recipient_member_id, status), letter(sender_member_id, created_at), person(owner_member_id) — 회원 스키마와 함께 생성
2. **페이지네이션**: 마음함·사람 목록 API에 커서 기반 (지금은 전체 반환)
3. **레이트리밋**: 발신 한도(하루 3명)를 지금은 count 쿼리로 봄 → 회원+Redis 도입 시 카운터로 (결정 #20의 Redis 도입 시점이 이때)
4. **알림**: 사용자 간 실시간 배달 알림은 로컬 알림으로 불가 → FCM 서버 푸시 전환 (P2-1과 함께)
5. AI 재작성: 요청당 ~1초·비용 <1원(Haiku) — 남용 방지로 회원당 일일 한도만. 캐시 불필요(입력이 매번 다름)
6. 먼 미래(만 단위 DAU): 읽기 복제본, 마음함 조회 캐시 — 지금 준비할 필요 없음

## 7. 로그인/회원가입 화면

- UI 구현됨(app/login.tsx): 카카오/Apple 버튼 + "로그인 없이 둘러보기" — 게스트 우선 원칙(마찰 최소화, #24와 일관)
- 실연동 순서: ① 카카오 개발자 콘솔 앱 등록(사용자 작업) → ② expo-auth-session 연동 → ③ 백엔드 Member+JWT → ④ Apple(iOS 심사 필수)
