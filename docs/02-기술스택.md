## 프론트엔드 선정 근거 (React Native vs Flutter vs 네이티브)

**React Native + TypeScript를 추천한다.**

1. **채용 시장**: 국내 대기업/유니콘 프론트엔드 채용의 중심은 **React + TypeScript** (네이버, 카카오, 토스, 당근, 배민 모두 React 계열). RN을 하면 React 생태계 역량이 그대로 이력서가 된다. Flutter/Dart는 잘 쓰는 회사도 있지만 채용 폭이 React보다 좁다.
2. **양대 스토어 배포**: 요구사항 충족. Expo EAS로 빌드·배포 파이프라인도 관리형으로 해결.
3. **개인 경험 자산**: 이미 sealo 프로젝트에서 RN + Expo를 사용 중 → 학습 비용 절감, 코드 패턴 재사용.
4. 잇다는 게임적 그래픽이 아니라 폼·리스트·텍스트 중심 UI → RN의 약점(고성능 그래픽)이 문제되지 않음.

상세 구성:
- Expo (managed workflow) + expo-router
- 상태 관리: Zustand + TanStack Query (서버 상태)
- 연락처: `expo-contacts` — **전체 동기화 금지, 선택적 불러오기만** (iOS limited access 대응, [00-리서치보고서](00-리서치보고서.md) §3)

## 백엔드 구성 (Spring Boot)

- Spring Boot 3.x, Java 21 (LTS, 가상 스레드)
- Spring Data JPA + QueryDSL
- Spring Security + JWT (+ OAuth2 Client: 카카오/구글/애플)
- 계층: Controller → Service → Repository, 도메인 중심 패키지 구조
- API 문서: SpringDoc(OpenAPI)
- 테스트: JUnit 5 + Testcontainers(PostgreSQL)

대기업 백엔드 채용 요건(Spring Boot·JPA·RDB·Redis·테스트)과 정확히 일치하는 구성이다.

## 관계 그래프를 어떻게 저장할까 (중요 결정)

리서치 결론([00-리서치보고서](00-리서치보고서.md) §4): **그래프 DB는 아직 필요 없다.**

- 개인당 관계 수는 수십~수백 명. "내 관계망" 조회는 PostgreSQL 일반 테이블 + 재귀 CTE로 충분
- Neo4j CE는 GPLv3 라이선스 논쟁이 있고, 운영 부담이 크다
- 스키마는 처음부터 그래프형으로 설계 (`person`, `relationship(from, to, type, status)`) → 훗날 그래프 DB 이관이 쉬움
- 그래프 분석(건너 건너 소개, 관계망 시각화 고도화)이 실제로 필요해지면 그때 JanusGraph(Apache 2.0) 또는 Neo4j 검토

## 민감 데이터 처리 원칙

갈등·추억·감정 기록은 최고 수준의 민감 정보다.

- 갈등/감정 기록 필드는 **애플리케이션 레벨 암호화**(AES-GCM) 후 저장, 키는 KMS 관리
- 상대방 실명 대신 이니셜/별칭 저장 옵션
- 연락처는 서버에 올리지 않는 것을 기본값으로 (선택 불러오기한 사람만, 해시 처리 검토)
- 로그에 관계·감정 데이터 절대 미포함
- 계정 삭제 시 완전 삭제 (개인정보보호법 준수)
